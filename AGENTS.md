# AGENTS.md

Guidance for AI coding agents working in this repository. See
<https://agents.md/> for the format. Human contributors should read
[README.md](README.md) first, then [TUTORIAL.md](TUTORIAL.md).

## What this project is

A **tutorial** Rust example that implements the BACnet **B-SS** (Smart
Sensor) profile using the CAS BACnet Stack's Rust `libloading` adapter: a
complete minimal, **read-only** BACnet/IP device (DS-RP-B, DM-DDB-B,
DM-DOB-B). Part of the BACnet profile example series, and the **first Rust
example** in it - the C++ sibling is `BACnetProfileExample-B-SS-CPP`, the C#
sibling is `BACnetProfileExample-B-SS-CS`, the Python sibling is
`BACnetProfileExample-B-SS-Python`; this example keeps the same objects,
names, and section layout as all three, but the binding mechanism is new:
lazy `libloading` symbol resolution plus free-standing `extern "C" fn`
callbacks, not an embedded C++ link, P/Invoke, or `ctypes`. The top priority
is that the code reads like a tutorial a customer can learn from and
copy-paste. Favour clarity over cleverness.

## Layout

This repository is self-contained:

- `src/main.rs` - the whole application, four numbered sections (§1
  configuration, §2 get callbacks, §3 interactive commands, §4 `main()`).
  There is no §2b/§2c - a B-SS registers no `Set*` callback and no
  `DeviceCommunicationControl` handler.
- `src/common/` - the shared Rust helper (`simple_udp.rs`,
  `cas_example_helper.rs`, `constants.rs`, `device_state.rs`), vendored in.
  Never edit here alone: once a second Rust example exists, a change must be
  swept to it too and `COMMON_VERSION` bumped with a `src/common/CHANGELOG.md`
  entry.
- `src/cas_bacnet_stack/` - the vendored Rust FFI adapter, copied from
  `submodules/cas-bacnet-stack/adapters/rust/` with one deliberate hand-edit
  (`load_library()`) - see `src/cas_bacnet_stack/README.md`. Everything else
  in that file is GENERATED by the stack's own tooling; do not hand-edit any
  other function in it - if the generated shape needs to change, that change
  belongs upstream in `cas-bacnet-stack`, then gets re-vendored here.
- `README.md` - what this example is. Keep it short and about THIS example
  only.
- `TUTORIAL.md` - how to extend and review the example. Long-form material
  that would bloat the README belongs here.
- `docs/PICS.md` - the Protocol Implementation Conformance Statement. Its
  objects-and-properties section is GENERATED from `docs/objects.json`; do
  not hand-edit between the `OBJECTS-PROPERTIES` markers.
- `docs/objects.json` - the input to that generator. Update it in the same
  change as any `src/main.rs` change that adds an object or a `get_property_*`
  branch.
- `submodules/cas-bacnet-stack` - the **CAS BACnet Stack** as a git submodule
  (private; tracks `6.x`). Its `source/`/MSVC build produce the
  separately-built native shared library this example loads via
  `libloading` at run time - see README.md "Build the native CAS BACnet
  Stack library". After cloning, run `git submodule update --init --recursive`.

The `PROFILE-TABLE` block in README.md is also generated, from the
example-series repository's `docs/profile-table.md`. Edit it there, not here.

## Build

```bash
git submodule update --init --recursive   # once, if not cloned with --recursive
cargo build --release                     # compiles this example + the vendored adapter mod
```

`cargo build` does **not** build the native CAS BACnet Stack library the
adapter `dlopen`s - that is a separate native C++ build (MSBuild on Windows
against `submodules/cas-bacnet-stack/projects/msvs/BuildCASBACnetStack.sln`
`/p:Configuration=ReleaseDll /p:Platform=x64`; g++ on Linux). See README.md
for the exact commands, and copy the result next to `target/release/`'s
compiled binary.

**Release only.** The vendored adapter's `load_library()` resolves
`CASBACnetStack_x64_Release{.dll,.so,.dylib}`; the stack's MSVC solution only
has a `ReleaseDll` configuration. Build and run this example in `--release`.
Do not "fix" this by adding a Debug DLL step here - that belongs in the stack
submodule, not this example.

**Must build with 0 warnings.** The one exception, already applied and
documented in place, is `#![allow(dead_code)]` at the top of
`cas_bacnet_stack_adapters.rs` (vendoring a 231-export generated binding
surface as a `mod` inside a `[[bin]]` crate - rather than the `[lib]` crate
its own header comment says it was checked against - makes `dead_code` fire
on every export this minimal example does not call; see the comment in that
file and in `src/cas_bacnet_stack/README.md`). Do not add another
`#[allow(...)]` anywhere else without the same in-place justification this
repository's few existing ones have.

## Run

```bash
cargo run --release -- --port 47821 --deviceID 12345   # run
cargo build --release                                   # compile-check (no separate typecheck step for a binary crate)
cargo clippy --release                                  # if clippy is installed - not part of the CI gate, but useful locally
```

Interactive commands while running (line-buffered - type + Enter; see
TUTORIAL.md "Interactive commands are a simplification"): `h` help, `q` quit,
`up`/`down` nudge Analog Input 1.

## Conventions

- Device is named "Rainbow"; objects use the series' colour names; vendor id
  389.
- Implement **only** the services and objects the B-SS profile requires -
  but expose **every required property** of each object.
- **This device is read-only.** There is no
  `BACnetStack_RegisterCallbackSetProperty*` call and no
  `SERVICE_WRITE_PROPERTY` anywhere in `src/main.rs`; do not add Set-side
  plumbing here - that belongs in a different profile example (B-SA/B-ASC).
- **Callbacks are plain `extern "C" fn` items, never closures.**
  `BACnetStack_RegisterCallbackGetProperty*` takes
  `Option<extern "C" fn(...)>` - a bare function pointer type a capturing
  closure cannot coerce to. Any device state a callback needs lives in
  `common::device_state::STATE` (a `once_cell::sync::Lazy<Mutex<DeviceState>>`),
  never a `main()`-local. See `src/common/device_state.rs`'s module doc
  before adding a new callback or a new piece of mutable state.
- **Every callback is wrapped in `std::panic::catch_unwind`**, returning the
  declining value (`false` for `Get*Property`, `0` for the transport
  callbacks) on a caught panic. An unguarded panic unwinding across an
  `extern "C" fn` into the native stack is undefined behavior - do not remove
  this wrapping to "simplify" a callback.
- Every `BACnetStack_*` setup call's return value is checked; failures print
  which call failed and exit non-zero (`std::process::ExitCode::FAILURE`).
- The stack PULLS: callbacks serve values through **raw pointers**
  (`*mut f32`, `*mut u32`, `*mut u8`), matching the native ABI directly - any
  function touching one of these pointers is `unsafe` at the point of use.
  Every `Get*Property` callback ends with a trailing `*mut u32 error_code`
  out-param (stack issue #974) - leave it alone on a catch-all `false`; set
  it only where this device knows the read is wrong (see the `State_Text`
  branch in `get_property_character_string`).
- The 6-byte IPv4 connection string (4 octets + BIG-endian port) is packed in
  `src/common/cas_example_helper.rs` only - never re-derive it.
- Links are identified by **Network Port object instance**, not by a
  transport-type enumeration. Unlike the C++/C#/Python editions, this
  instance (`common::constants::NETWORK_PORT_INSTANCE`) is a compile-time
  constant, not a parameter threaded through `register_common_callbacks()` -
  because the transport callbacks that need it are themselves plain
  `extern "C" fn` items that cannot capture a parameter either. Keep it that
  way; do not "fix" this into a runtime parameter without also solving how a
  free function would read it (a second static, most likely).
- Reuse the constants already defined in `src/common/constants.rs`
  (`OBJECT_TYPE_*`, `PROPERTY_IDENTIFIER_*`, `SERVICE_*`, ...) rather than
  hand-writing a numeric literal inline - unlike the C#/Python editions,
  the vendored Rust adapter defines **none** of these itself, so
  `constants.rs` is the complete, authoritative set for this project.
- Present tense only: no comment or doc references a previous version of this
  example or of the stack.
- **Never edit `src/common/` in this repo alone once a sibling Rust example
  exists** - it will be a vendored copy shared across the series, with its
  own version (`COMMON_VERSION`) and changelog (`src/common/CHANGELOG.md`).
- **Never hand-edit `src/cas_bacnet_stack/cas_bacnet_stack_adapters.rs`
  beyond `load_library()`** - it is a generated file, vendored verbatim
  otherwise. If you need a callback/export shape this file does not have,
  that is a stack submodule change, not something to patch around here.

## How to verify a change

There are no unit tests; verification is behavioural:

1. `cargo build --release` with 0 warnings, 0 errors.
2. Smoke: with the native library built and copied next to
   `target/release/`'s output (see README.md), `cargo run --release --
   --port 47821` stays up past the "ready" banner (every failed setup call
   exits non-zero, so "still running" proves registration).
3. Read back what you changed with a BACnet client (Who-Is, ReadProperty of
   every required property; confirm a WriteProperty is rejected).
4. If you changed the objects or their properties, regenerate
   `docs/PICS.md` (`python tools/gen-objects-properties.py
   BACnetProfileExample-B-SS-Rust` from the series root) and confirm no row
   comes out flagged with ⚠.

## Releasing

Bump `APP_VERSION` in `src/main.rs` (and the `version` field in `Cargo.toml`)
and add an entry to [CHANGELOG.md](CHANGELOG.md), then tag `vX.Y.Z`. The
GitHub Actions workflow builds the native library, builds + smoke-tests the
Rust project, and publishes a release.

## A note on this stack's Rust adapter's CI history

`cas_bacnet_stack_adapters.rs`'s own header says no CI gate in the
`cas-bacnet-stack` repository compiles it; it was checked once, by hand
(#1483, 2026-09-12), against its own standalone `Cargo.toml`. This example's
`.github/workflows/release.yml` running `cargo build --release` against the
vendored copy is, as far as this project is aware, the **first automated
compilation gate** the Rust adapter has ever had. Treat any *future* change
to the vendored files in `src/cas_bacnet_stack/` (a re-vendor from a newer
stack commit, for instance) as unverified again until this workflow (or
another automated Rust build) re-checks it - do not assume a newer generated
file compiles clean just because this one does.
